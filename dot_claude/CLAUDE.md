# 開発指針

一貫性、可読性、保守性を重視しシンプルな実装を心がける。
不明瞭な指示は質問を行い明確にする。
公式ドキュメント等の1次ソースをまず調査する。
非自明な変更では、実装に着手する前にインターフェース仕様（シグネチャ・型・エラー仕様など）を確定する。

# 出力の方針

応答は焦点を絞り簡潔にする。前置き・留保・注意書きは短くし、本題に文量を割く。説明を求められたときは、詳細を明示的に求められない限り要点の概観を返す。
最初のツール呼び出しの前に、これから何をするかを1文で述べる。作業中の途中報告は、重要な発見があったときか方針を変えたときだけ行う。完了時は結果を先に述べ、補足を後に置く。
ファイルに書き出す成果物（レポート・ドキュメント・コミットメッセージ・PR ボディ）の長さは内容に見合わせる。実質を書き、埋め草のセクション・重複する要約・boilerplate で膨らませない。

# GitHub の記法

同一リポジトリの issue / PR を参照するときは `#123` 形式かフル URL をそのまま使う（`redirect.github.com` 経由にすると `Fixes #123` などのクローズキーワードが認識されず、マージ時の自動クローズが働かない）。
作業リポジトリが `yami-beta/*` のときに限り、他リポジトリへのリンクは `https://redirect.github.com/{org}/{repo}/...` に書き換えてバックリンク通知を避ける。`yami-beta/*` 以外のリポジトリで作業しているときは書き換えずそのまま使う。
https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/autolinked-references-and-urls#avoiding-backlinks-to-linked-references

# 実装・レビュー・テスト方針

設計・計画・インターフェース仕様（シグネチャ・型・エラー仕様など）の確定はメインが行い、確定した仕様に基づく実装は `implementer` に委譲する。`implementer` は既定で Sonnet が走る。多ファイルにまたがる機能追加・大きめのリファクタ・難易度の高い実装は Agent ツールの `model` に `opus` を指定して起動し、仕様が確定した局所的な実装は既定のままでよい。
テストは実装をなぞらず仕様・インターフェースに対して書くものであり、実装完了を待つ必要はない。インターフェース仕様確定後は、`implementer` と `test-author` を Agent ツール（`run_in_background: true`）で並行起動する。
実装担当・レビュアー・テスト担当には仕様・変更の意図・対象ファイル・制約を必ず渡す（隔離コンテキストには要約しか伝わらないため）。`code-reviewer` には加えて差分（`git diff` の出力）をプロンプトに含める（Bash を持たず自力で差分を取得できないため）。
`code-reviewer` によるレビューは実装とテストの両方が完成してからまとめて行う（レビューは実装完了に依存するため並行不可）。自己正当化バイアスを排除するため、実装を書いたコンテキストとは別エージェントに行わせる。
小さな変更・自明な修正では上記を省略し、メインが直接実装する。一握りのツール呼び出しで終わる作業は委譲しない。1体で足りるなら複数起動しない。自分の作業の再確認・二重チェックを目的にサブエージェントを使わない（`code-reviewer` は実装者とは独立したレビュアーであり、これには該当しない）。
`code-reviewer` のレビュー結果は要約に圧縮せず、各指摘（深刻度・場所・問題・対応方針）の一覧をそのまま会話に提示してから修正に進む（サブエージェントの返り値は tool result として親に返るだけでユーザーの画面には出ず、Ctrl+O でも展開されないため）。
blocker / major の指摘は修正後、修正差分を添えて `code-reviewer` に再レビューを依頼する（minor / nit は修正のみでよい）。
実装完了を宣言する前に、変更を実際に動かすエンドツーエンドの動作確認を行う（テストが green であることだけで完了としない）。

# コンテキスト・並行性の方針

広範囲にまたがる大きな調査・探索はサブエージェント（Explore 等）に委譲し、メインのコンテキストは設計判断とオーケストレーションに温存する。ただし委譲は「独立していて規模のある作業」に限る（1M コンテキストが既定になり、コンテキスト節約のみを理由とした委譲の必要性は下がった）。
サブエージェント起動時は effort を作業に合わせる（重い実装・長時間の agentic 作業は `xhigh`、機械的な作業は `low` / `medium`）。
互いに独立した複数タスクはバックグラウンドエージェントや Agent Teams で並行実行する。その際、各エージェントの編集対象ファイルが重ならないようにタスクを分割し、重なる場合は並行にせず順次実行する。git worktree は管理負担が大きいため使わない。
多数ファイルへの同種の変更やコードベース全体の監査など「同じ作業 × N」の仕事は、Workflow によるオーケストレーションが有効か検討し、ユーザーに提案して承認を得てから実行する。

# メモリ運用

作業方針についてユーザーから修正・指摘を受けたとき、またはプロジェクト固有の非自明な知見（ハマりどころ・環境制約・設計上の経緯）を得たときは、永続メモリに保存してセッションをまたいで引き継ぐ。
メモリは一時的な受信箱であり、真実の源は git 管理のファイル（CLAUDE.md・スキル・settings）に置く。メモリの知見が繰り返し役立ったら CLAUDE.md やスキルへの昇格を提案してコミットし、昇格済みの内容はメモリから削除する（二重管理は陳腐化の温床）。
スキルの実行中に手順の不備・毎回発生する手直し・ユーザーからの修正があったときは、その場しのぎで終わらせず、該当スキル（SKILL.md）自体の改善を提案する。

# スキルの管理

ユーザースコープのスキルの正本は https://github.com/yami-beta/skills の `skills/<name>/SKILL.md` であり、`gh skill` で `~/.claude/skills/` へ導入する（chezmoi は管理しない）。
`~/.claude/skills/` にあるのは `gh skill install` が置いた複製であり、直接編集しない（`gh skill update` で無言のうちに上書きされる。frontmatter の `metadata.github-*` は install 時に注入されたもので、リポジトリ側には持たせない）。
スキルを改善するときは skills リポジトリを編集して main へ入れ、`gh skill update --all` で反映する。リリースタグは切らない運用のため main の HEAD が常に取得される。
スキルは単体で完結させる（外部の CLAUDE.md に依存する記述を置かない）。変更後は skills リポジトリで `gh skill publish --dry-run` を実行し、error が出ないことを確認する。

# Proactive loops の活用方針

Proactive loops は、イベントやスケジュールをトリガーに、人間の承認を待たずゴール達成まで自律実行し、ゴールに到達した回で終了する自動化であり、バグ報告のトリアージや依存関係アップグレードの確認など、反復的でゴールが明確な作業に向く。判断基準が曖昧な作業や、影響が大きく都度の確認が必要な作業には使わない。
常設のトリガーには `/schedule` を使う。セッション限定でよい一時的な定期実行・リマインドには `CronCreate` を使う（セッション限定・7日で失効し、変化の監視には向かないため、監視したい場合は `Monitor` を使う）。`/loop` は一定間隔の再実行または自己ペースの継続であり、ゴール達成で自律停止するわけではないため Proactive loop の代替にはならない。
完了条件は `/goal` で定義する（各ターン終了後にモデルが達成を判定し、満たされるか `/goal clear` するまで自動的にターンを継続する）。スケジュール起動された回は前回の会話を記憶していないため、`/schedule` のプロンプト自体にもゴールと検証手段を自己完結で書き切る。探索や判定を並列化したい場合は「コンテキスト・並行性の方針」に従い Workflow でオーケストレーションする。
Auto mode（承認なしの自動実行）で回す範囲は、permissions/defaultMode で対象コマンドを明示的に絞った上に限定する。破壊的操作・外部送信・公開範囲の変更を伴うタスクは Proactive loop 化せず、都度の確認を残す。
